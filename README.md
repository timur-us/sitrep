# SITREP

**SITREP** (situation report) is an advisor copilot for **Feistel Private Bank**, a fictional German private bank. It prepares a relationship manager for a client call with cited answers over their own mandates, drafts the follow-up, and executes side effects only after human approval — built around an own agent harness and red-teamed against real attack patterns.

> Fictional bank, synthetic data. Nothing here is a real institution, person or record.

*Know your client before the call.*

Status: M0, the local foundation, closes with PR 9; its report, with what is shaky and what M1 inherits, is `docs/reports/m0.md`. M1, the MVP core, is next. To get from a fresh clone to green: `docs/runbooks/local-setup.md`, "From a fresh clone". See `docs/brief.md`, `docs/threat-model.md`, `docs/discovery.md` and `redteam/SCOPE.md`. Decisions are recorded in `docs/decisions/` (ADRs).

## Local database

`make up` starts PostgreSQL 17 with pgvector in Docker Compose, `make migrate` applies `db/migrations` as the migration role, and `make test` needs both (and the embedding model, below). The database uses trust auth for all connections into the container, reachable only through a 127.0.0.1 publish (port 55432): a local convenience for synthetic data. Azure is Entra-only from M3. On Linux, use Docker Engine 28 or later; earlier engines expose localhost-published ports to the local network segment. To see the server, run `docker compose exec db psql -U postgres -d sitrep -c 'SELECT version()'` (PostgreSQL 17.11). Roles and migrations: ADR 0008 and `docs/runbooks/local-setup.md`. The five advisor tables (`advisors`, `mandates`, `mandate_contacts`, `documents`, `chunks`) have row-level security, forced on their owner too: the app role sees an advisor's rows only inside a transaction that names that advisor, and zero rows otherwise. `product_sheets`, the one global table, is read inside any advisor transaction and written by the owner alone. The residual risk (a forged `set_config` through SQL injection) and its mitigations are in `docs/threat-model.md`.

## Harness interfaces (M0)

`app/harness/` holds what the M1 agent loop builds on: a tool registry that refuses a tool with an identity field (`advisor`, `user`, `berater`, `benutzer`, `mitarbeiter` and the other terms of the plan, in any spelling), an arguments model that is not frozen, an open schema, a read tool whose result is not marked untrusted, or a drafting or side-effect tool without approval; the four MVP tools, declared only; `Untrusted[T]`, a tool result that is not rendered by accident (`str`, `format`, `+` and `repr` all refuse to show it), with `wrap()` as the one sanctioned way to the text, inside a delimiter the text cannot close; and the approval, policy, model and token-budget interfaces. `app/embeddings/` has the embedder interface and a deterministic fake that cannot pass for the real model. Nothing calls a model yet. Details: `docs/runbooks/local-setup.md`, "The harness (M0)".

## Synthetic corpus (M0)

`make data` regenerates the synthetic corpus into `data/synthetic/out/` (git-ignored), offline, from the standard library, branding and a fixed seed, so two runs give the same bytes: three advisors, 40 mandates (the Weber family among Alice's 14), and per mandate a KYC profile, a portfolio report, call notes and mailbox e-mails, plus six global product sheets, about 70 % German. Each document carries its origin and trust, set from its type: the mailbox is always untrusted. No IBAN, phone number, street address or domain outside `feistel.example`, and no attack content. Details: `docs/runbooks/local-setup.md`, "The synthetic corpus (M0)".

## Loader (M1)

`make load` writes the corpus into the database (after `make up` and `make migrate`; it runs `make model` and `make data` itself). It takes only the reviewed corpus, whose manifest hash is pinned, and checks every record first. The app role only reads, so the loader logs in as the migrator, acts as the owner, and writes one advisor per transaction through a helper that request code cannot reach; row-level security still scopes every row. Each document carries its `origin`, and its `trust` is generated by the database, never written. A second load gives the same rows. ADR 0010; details in `docs/runbooks/local-setup.md`, "The loader (M1)".

## Embedding model (M1)

`make model` downloads the three pinned files of `intfloat/multilingual-e5-small` (about 490 MB) from Hugging Face into the git-ignored `models/` and checks each sha256; `make test` needs it, as it needs the database. The embedder runs on the CPU in onnxruntime and loads only bytes whose hash matches, after a check of the ONNX graph that refuses external data and non-standard operators; nothing downloads at runtime. Passages are cut with the model's own tokenizer to 400 tokens or fewer. ADR 0005; details in `docs/runbooks/local-setup.md`, "The embedding model (M1)".

## The model client (M1)

`app/harness/model_client.py` builds the one client for the Messages API (Sonnet 5.5, `SITREP_MODEL`). The key is `ANTHROPIC_API_KEY` in your own `.env`, from a Console workspace with a spend limit; tests never need it, and without it the app starts. `python -m app` refuses to start (exit 2, before binding, naming the variable) while any other `ANTHROPIC_*` variable is set, while the key itself is exported, and while `PYDANTIC_SETTINGS_DEBUG` is set. The client sends only to `https://api.anthropic.com`, ignores proxy variables, follows no redirect, retries nothing and keeps the SDK's spans and debug logs off. [ADR 0012](docs/decisions/0012-api-key-and-model-client.md); details in `docs/runbooks/local-setup.md`, "The model client (M1)".

## Dev login (M0)

Until Entra ID in M3, `SITREP_DEV_AUTH=1 uv run python -P -m app` adds a local login at `http://127.0.0.1:8000/dev/login` for the three synthetic advisors; `/api/mandates` then lists the signed-in advisor's mandates, scoped by row-level security. The entry point refuses it (exit 2, before binding) on any host but exactly `127.0.0.1`, and the image does not carry it. Every request needs `Host: 127.0.0.1:<port>`, every POST an `Origin` of exactly `http://127.0.0.1:<port>`; sessions live in process memory behind an HttpOnly, SameSite=Strict cookie, and no header or query parameter can name the advisor. The settings' variables carry the prefix `SITREP_` (`SITREP_HOST`, `SITREP_PORT`, `SITREP_DEV_AUTH`, `SITREP_TRACE_PLAINTEXT`). ADR 0009; details in `docs/runbooks/local-setup.md`, "The dev login (M0)".

## What this project shows, and what it does not

This section is a promise for the finished project. Each item names the milestone that delivers it; until then it is a plan, not a result.

### Shows

- **An own agent harness** on the Anthropic Messages API: a tool registry with declared effects, side effects only after the advisor approves, untrusted retrieval results wrapped with provenance, and traces without prompt plaintext (interfaces and traces M0, the loop M1, hardening M2; ADR 0001, ADR 0007).
- **An advisor boundary enforced by the database**: row-level security in PostgreSQL scopes every query to the logged-in advisor's own mandates, not the prompt (M0 schema and tests, M1 retrieval).
- **Measured red teaming**: the attack success rate of the EchoLeak pattern (prompt injection through an e-mail) in English and German, before and after each hardening layer, from a recorded corpus (M1 unhardened, M2 hardened).

### Does not show

- **Production readiness.** It is a single-region demo with a small Azure footprint from M3, not a bank system.
- **Real data.** The bank is fictional and every record is synthetic. No real client data, mailbox or CRM is ever connected.
- **Legal advice.** The regulatory notes in `docs/brief.md` are an engineering view.
- **EU-only inference.** The default route to the model has no EU-only option; the exits are documented in ADR 0003.
- **Network-level egress control.** No VNet, NAT or firewall; egress is controlled in the application only (`docs/threat-model.md`).
